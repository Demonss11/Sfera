# Сфера

Полностью кириллический язык программирования — компилятор написан на
Rust, компилирует в машинный код через LLVM.

```
функция главная() -> целое {
    вывести("Привет, мир!");
    вернуть 0;
}
```

## Что уже умеет язык

- Компиляция в нативный машинный код (не интерпретатор)
- Автоматическое управление памятью для структур (ARC), без ручного
  `free`/`delete`
- Обобщённые типы: `Список<T>`, `Словарь<Ключ, Значение>`, пользовательские
  обобщённые структуры
- Обработка ошибок через `результат<T>` (без исключений)
- Настоящий полиморфизм через контракты (динамический диспетчинг,
  таблицы виртуальных методов)
- Многопоточность: `параллельно { }` и `канал<T>` для безопасной
  передачи значений между потоками
- Модули (`подключить`) и пакетный менеджер (`сфера_пакеты`)
- Прямая работа с C-библиотеками через FFI (`внешняя функция`)
- Интерполяция строк: `"Привет, $имя!"` и `"Итог: ${а + б}"` — результат
  полноценный текст (можно сохранить в переменную, вернуть, передать
  куда угодно), а не только напечатать напрямую
- Отладчик: флаг `-g`/`--отладка` встраивает настоящую DWARF-отладочную
  информацию — точки останова по номеру строки, пошаговое выполнение и
  стек вызовов работают в **обычном lldb/gdb**, без своего отдельного
  инструмента
- Отслеживание (наблюдаемость), все три задуманных шага: структурированные
  логи с уровнями и меткой времени (`стандартная_библиотека/лог.код`),
  метрики — счётчики и измерители с экспортом в формате Prometheus
  (`стандартная_библиотека/метрики.код`), и трейсинг — вложенные спаны с
  деревом длительностей (`стандартная_библиотека/трейсинг.код`)
- Работа с сетью — TCP-сокеты напрямую через системные вызовы: и
  клиент, и полноценный HTTP-сервер (маршрутизация, параллельная
  обработка подключений)
- Собственное хранилище данных «ключ → значение» — без единой внешней
  библиотеки: индекс в памяти, компактификация старых записей
- **[Первый сайт языка](сайт/)**, работающий на самой «Сфере» — HTTP-сервер
  и хранилище данных вместе, никакой внешней веб-инфраструктуры
- Кросс-компиляция под другие архитектуры процессора (например, ARM64)
  — реально проверено через эмуляцию и на настоящем Android-устройстве
- Полноценная среда разработки с графическим интерфейсом — для macOS
  ([`инструменты/панель-разработчика/панель.код`](инструменты/панель-разработчика/))
  и для Android ([`инструменты/android/панель_android.код`](инструменты/android/))
- ✅ **Компилятор «Сферы» полностью работает внутри обычного,
  легально подписанного Android-приложения — без root, без Termux,
  без внешней оболочки.** Сам компилятор (кросс-собранный под ARM64),
  свой линковщик (`ld.lld`) и небольшая замена `clang` зашиты прямо в
  APK; приложение на устройстве компилирует, линкует и **запускает**
  код «Сферы» самостоятельно, в собственной песочнице. Подтверждено
  многократно через `adb logcat` на настоящем устройстве.
- Эта возможность уже встроена в основную панель-приложение
  (`инструменты/android/панель_android.код`, вкладка «Запуск») — можно написать код прямо
  в приложении и увидеть результат его реального выполнения на
  телефоне ⚠️ обновлённая сборка панели ещё не проверена вживую (сам
  компилятор и линковка — проверены отдельно, многократно; сборка,
  где всё это подключено к интерфейсу панели — нет)
- ✅ **Компилятор впервые реально собран и проверен на настоящей Windows**
  (x86-64): ставится скриптом `установить-windows.ps1` (LLVM 18 + Clang 18
  + Build Tools), и скомпилированные им программы компилируются, линкуются
  и запускаются штатной командой `запустить файл.код`. Для этого добавлен
  минимальный слой совместимости pthread поверх Win32
  (`совместимость/pthread_win.c`), подключаемый автоматически. Подробности
  и честные ограничения — в ИСТОРИЯ_РАЗРАБОТКИ.md.
- Экспериментальная поддержка запуска без операционной системы (на
  голом железе)
- `прервать`/`продолжить` в циклах `пока` и `для каждого`
- `Список<T>.удалить(индекс)` — удаление элемента со сдвигом хвоста
  (корректно освобождает удаляемый элемент, если это структура)
- `Список<T>.освободить()` — как и у `Словарь`, явное освобождение
  памяти (список сам по себе не освобождается автоматически); для
  элементов-структур дополнительно корректно отпускает ARC-счётчик
  каждого элемента
- ✅ **Исправлен настоящий use-after-free** (не просто утечка, как
  считалось раньше): `Список<Контракт>.добавить(...)`/`.получить(...)`
  теперь корректно захватывают (ARC-retain) элемент — подтверждено
  воспроизведённым и устранённым крахом под valgrind ("Invalid read...
  freed")
- ✅ `Список<Контракт>.удалить(...)`/`.освободить()` теперь тоже
  корректно ОСВОБОЖДАЮТ свои элементы (тем же способом, что и обычные
  структуры) — раньше, после исправления use-after-free выше, элементы
  корректно захватывались, но никогда не освобождались (честная утечка,
  задокументированная и теперь устранённая): конкретная структура за
  толстым указателем неизвестна на этапе компиляции, поэтому она
  определяется в рантайме сравнением адреса vtable
- ✅ Устранена и последняя утечка в категории "текст, возвращаемый
  методом, но не освобождаемый": `объект.метод()`, где `объект` —
  переменная КОНТРАКТНОГО типа (динамическая диспетчеризация), — раньше
  результат такого вызова никогда не распознавался как владеющий текст
  (конкретная реализация неизвестна на этапе компиляции). Теперь
  распознаётся: если ВСЕ структуры, реализующие контракт, уже доказанно
  возвращают свежий буфер для этого метода — результат динамического
  вызова тоже безопасно освобождается, независимо от того, какая именно
  реализация выполнится в рантайме
- ✅ Устранена утечка текста, возвращаемого ПОЛЬЗОВАТЕЛЬСКИМИ функциями
  и МЕТОДАМИ (`функция сгенерировать(...) -> текст { ... }`,
  `объект.метод()`) — вероятно, самый часто задеваемый случай утечки
  текста из всех найденных: раньше результат такой функции/метода не
  освобождался ни при сохранении в переменную, ни при прямой передаче
  в вызов
- ✅ **Исправлен настоящий double-free**, найденный при проверке
  предыдущего пункта: считать функцию/метод "гарантированно
  возвращающей новый буфер текста" по одной лишь ДЕКЛАРАЦИИ типа
  возврата (`-> текст`) оказалось небезопасно — метод вида
  `функция сказать() -> текст { вернуть "Мяу"; }` возвращает строковый
  литерал (никогда не malloc'нутый), и попытка его `free()` разрушала
  аллокатор. Исправлено анализом ТЕЛА функции/метода вместо декларации
  — подробности и честно указанные оставшиеся ограничения (например,
  метод, вызванный через контракт, по-прежнему не покрыт) в
  ДОКУМЕНТАЦИЯ_ЯЗЫКА.md
- ✅ **Исправлена ещё одна найденная попутно утечка**: локальная
  переменная КОНТРАКТНОГО типа (`Печатаемый а = создать_питомца(1);`)
  никогда не освобождалась при выходе из области видимости — в отличие
  от переменной конкретного структурного типа. Заодно найден и устранён
  сопутствующий риск двойного освобождения при копировании такой
  переменной. Подробности в ДОКУМЕНТАЦИЯ_ЯЗЫКА.md
- ✅ `Список<текст>.добавить(...)` и `Словарь<Ключ, Значение>.положить(...)`
  теперь всегда сохраняют самостоятельно владеемую копию текста
  (`strdup()` заимствованного значения, если оно не свежий буфер),
  поэтому `.освободить()` у обоих может безопасно освободить каждый
  элемент — раньше это было невозможно отличить от освобождения
  строкового литерала (краш). Заодно устранена отдельная утечка:
  повторное `положить(...)` с уже существующим ключом раньше не
  освобождало старое текстовое значение при перезаписи.
- ✅ **Исправлен настоящий use-after-free между потоками**:
  `канал<текст>.отправить(...)` раньше не копировал содержимое текста
  вообще (только 8 байт адреса) — отправленное значение оставалось тем
  же буфером, что и локальная переменная потока-отправителя, которая
  освобождается как обычно при выходе из области видимости, независимо
  от отправки. Получатель в другом потоке читал уже освобождённую
  память — подтверждено воспроизведённым крахом под valgrind
  ("Invalid read" на памяти, `free()`-нутой другим потоком).
  Исправлено: `отправить(...)` теперь всегда делает независимую копию
  (`strdup()`) перед передачей через канал, независимо от того,
  "свежее" ли переданное значение.
- ✅ Устранены и обе честные утечки, оставшиеся после исправления выше:
  текст, полученный через `канал<текст>.получить()`, теперь
  освобождается автоматически (распознаётся как владеющее значение),
  а у `канал<T>` появился метод `.освободить()`, освобождающий сам
  объект канала (раньше такого способа не существовало вообще).
  ⚠️ Честно осталось: неполученный текст в канале на момент
  `.освободить()` всё равно утекает — подробности в
  ДОКУМЕНТАЦИЯ_ЯЗЫКА.md
- ✅ Устранены оба честных, узких ограничения
  `дождаться_поток(номер)`: раньше был нужен строгий порядок вызовов
  относительно `дождаться_все_потоки()`, и нельзя было вызвать дважды с
  одним номером (оба случая — неопределённое поведение POSIX, двойной
  `pthread_join`). Теперь оба сочетания безопасны: повторный/лишний
  join для уже присоединённого потока — просто no-op
- ✅ **Исправлен настоящий use-after-free**: переприсваивание УЖЕ
  СУЩЕСТВУЮЩЕЙ переменной структурного или контрактного типа
  (`а = Кот(2);` или `а = б;`, в отличие от нового объявления) вообще
  не трогало ARC — старое значение не освобождалось, новое (если было
  копией другой переменной) не захватывалось, что при выходе из
  области видимости приводило к двойному освобождению одного и того же
  объекта. Найдено целенаправленной проверкой в рамках общего наведения
  языка на стабильность, воспроизведено и устранено под valgrind
- ✅ Устранена задокументированная утечка памяти: текстовый результат,
  переданный напрямую (без промежуточной переменной) в `вывести(...)`,
  в обычный/квалифицированный вызов функции, в вызов МЕТОДА (включая
  динамический вызов через контракт), или в `длина`/`содержит`/`найти`/
  `подстрока` — теперь освобождается автоматически везде перечисленном
  (раньше утекал при каждом таком вызове). ⚠️ Пока не покрыты методы
  `Список<T>`/`Словарь<Ключ, Значение>`/`канал<T>` (`добавить`, `положить` и
  т.п.) — они забирают владение аргументом, там нужен другой подход
- ✅ **Исправлен фундаментальный баг стабильности**: любая переменная,
  объявленная внутри цикла или вложенного `если`, раньше медленно
  «утекала» стек на каждой итерации (классическая ловушка LLVM —
  `alloca` не в начале функции выделяет НОВОЕ место при каждом
  повторном выполнении, а не одно на весь вызов) — после достаточного
  числа итераций (проверено: около полумиллиона) программа падала с
  переполнением стека без единой ошибки компиляции. Исправлено во всём
  компиляторе разом: теперь все служебные и пользовательские
  переменные размещаются в начале функции, как и в любом серьёзном
  компиляторе. Затрагивало практически любой цикл с достаточным числом
  итераций — один из самых значимых багов стабильности, найденных за
  всё время разработки.
- ✅ **Интерполяция строк доведена до полноценной, а не осталась узким
  трюком**: раньше `"Привет, $имя!"` работал ТОЛЬКО как прямой
  единственный аргумент `вывести(...)` (строился напрямую в printf-формат,
  без runtime-конкатенации строк) и поддерживал только простую форму
  `$имя` — нельзя было ни сохранить результат в переменную, ни передать
  в другую функцию, ни вставить произвольное выражение. Теперь:
  интерполяция строит настоящее текстовое значение через ту же
  конкатенацию, что и `"+"`, — используется где угодно, как любой другой
  текст; добавлена форма `${выражение}` для произвольных выражений
  (не только имени переменной) любого форматируемого типа (текст, целые
  числа любой разрядности, дробное, верно). Честно осталось: строковые
  литералы внутри `${...}` не поддержаны (архитектурное ограничение
  однопроходного лексера — подробности в ДОКУМЕНТАЦИЯ_ЯЗЫКА.md).
- ✅ **Появился отладчик**: `запустить программа.код -g -c` встраивает в
  объектный файл настоящую DWARF-отладочную информацию (через LLVM
  `DebugInfoBuilder`, тот же механизм, что использует clang) — точки
  останова по номеру строки, `next`/`step`, честный стек вызовов (`bt`) и
  просмотр исходного кода прямо в **lldb или gdb** — без своего
  собственного, отдельного инструмента отладки. Проверено напрямую: и
  lldb, и gdb корректно останавливаются на нужной строке, шагают по коду
  и строят стек вызовов через несколько функций и поток `параллельно`.
  ⚠️ Честно осталось на будущее: просмотр значений локальных переменных
  ПО ИМЕНИ (`print x`) пока не поддержан — требует отдельного описания
  DWARF-типов для каждого типа «Сферы» (структуры, `Список<T>`,
  контракты). Подробности и ограничения — в ДОКУМЕНТАЦИЯ_ЯЗЫКА.md.
- ✅ **Система отслеживания (наблюдаемости), все три задуманных шага**:
  структурированные **логи** (`стандартная_библиотека/лог.код`) —
  уровни (отладка/инфо/предупреждение/ошибка/критическая), точная
  метка времени (год-месяц-день час:минута:секунда, посчитана
  собственным алгоритмом, без внешних зависимостей — см.
  ДОКУМЕНТАЦИЯ_ЯЗЫКА.md), вывод в консоль и/или дозапись в файл.
  Фундамент — компиляторный builtin `юникс_время()`. **Метрики**
  (`стандартная_библиотека/метрики.код`) — счётчики и измерители,
  экспорт снимка в текстовом формате Prometheus. При написании метрик
  найдены и исправлены два реальных бага компилятора (`Список<T>` как
  поле структуры не поддерживал `объект.поле.метод(...)`; числовое
  `а + б` внутри аргумента вызова ошибочно считалось текстовой
  конкатенацией и приводило к `free()` на числовом значении — подробности
  и то, как найдено, в ИСТОРИЯ_РАЗРАБОТКИ.md). **Трейсинг**
  (`стандартная_библиотека/трейсинг.код`) — вложенные именованные спаны
  с человекочитаемым деревом длительностей, та же модель, что в
  OpenTelemetry/Jaeger/Zipkin. Фундамент — новый компиляторный builtin
  `монотонное_время_нс()` (монотонные часы, наносекундная точность —
  секундная точность `юникс_время()` не годится для длительностей).
  Оба снимка теперь доступны и по HTTP — рабочий пример
  `examples/веб/наблюдаемость_http.код`: `/metrics` отдаёт формат
  Prometheus напрямую (настоящий Prometheus-сервер может скрейпить без
  переделки), `/trace` — дерево трейсинга уже обработанных запросов.

## Как всё это появилось

**[ИСТОРИЯ_РАЗРАБОТКИ.md](ИСТОРИЯ_РАЗРАБОТКИ.md)** — подробный дневник
разработки: что было решено и почему, какие баги были найдены (включая

компилятора изнутри, а не только конечный результат.

## Сборка

```bash
cargo build --release
```

Требуется LLVM 18 (`LLVM_SYS_180_PREFIX` должен указывать на его
установку). Готовые скрипты: `собрать.sh` (macOS/Linux, пересобирает
компилятор и обновляет команду `запустить`), `собрать-android.sh`
(кросс-компиляция под Android, не проверена вживую), `установить-windows.ps1`
(установка с нуля на Windows).

### Windows (x86-64)

`установить-windows.ps1` ставит всё необходимое с нуля и уже **проверен
вживую** на настоящей Windows-машине — компилятор собирается, а
скомпилированные им программы компилируются, линкуются и запускаются.
Скрипт устанавливает Visual Studio Build Tools (компонент C++), LLVM 18
(`vovkos/llvm-package-windows`, только X86) и отдельно Clang 18 (пакет LLVM
его не содержит, а он нужен самому компилятору для финальной линковки),
затем прописывает PATH. Два Windows-специфичных момента:

- При сборке **самого компилятора** `inkwell` подключается без фичи
  `target-all` — готовый пакет LLVM под Windows собран только с X86, иначе
  линковка падает десятками `unresolved external symbol: LLVMInitializeARM…`
  и т.п. (см. `Cargo.toml` — раздельные таблицы зависимостей по платформе).
- Сгенерированный код всегда обращается к pthread-примитивам (глобальный
  mutex/cond), которых в Windows нет. Поэтому при линковке нативных
  Windows-программ компилятор **автоматически подключает** слой совместимости
  `совместимость/pthread_win.c` (pthread поверх
  `CRITICAL_SECTION`/`CONDITION_VARIABLE`/`CreateThread`) — вручную добавлять
  ничего не нужно.

Честные ограничения Windows-сборки: кросс-компиляция под другие архитектуры
(например, ARM64/Android) с Windows недоступна — в пакете LLVM только X86;
графика (SDL2) и примеры с базой данных (SQLite) требуют отдельной установки
этих библиотек; слой совместимости покрывает mutex/cond/потоки/`sleep`.

## Структура репозитория

- `src/` — сам компилятор (лексер, парсер, семантика, кодогенерация) и
  вспомогательные бинарники: `src/bin/сфера_lsp.rs` (языковой сервер для
  редакторов) и `src/bin/сфера_пакеты.rs` (пакетный менеджер)
- `стандартная_библиотека/` — встроенные модули (`сеть`, `хранилище`,
  `графика`, `база_данных`, `память`) — обязана лежать в корне
  репозитория, компилятор ищет её по относительному пути от бинарника
- `examples/` — рабочие примеры кода на «Сфере», от «Привет, мир!» до
  многопоточности, модулей и запуска на голом железе
- `сайт/` — [первый сайт языка](сайт/), написанный на самой «Сфере»
- `инструменты/` — приложения поверх языка, не часть самого компилятора:
  `панель-разработчика/` (среда разработки с графическим интерфейсом для
  macOS) и `android/` (Android-версия панели и тестовые файлы для неё)
